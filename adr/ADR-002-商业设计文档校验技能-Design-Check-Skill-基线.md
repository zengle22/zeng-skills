# ADR-002：Pre-SSOT 文档校验技能（Design Check Skill）基线

> **SSOT ID**: ADR-002
> **Title**: 建立 Pre-SSOT 阶段 6 大维度文档校验技能，采用纯 LLM + 结构化输出架构，覆盖商业设计、产品设计、UX 设计、架构设计、测试设计、工程实施全维度及跨维度一致性，确保 Pre-SSOT 输入充分后再进入 SSOT 形式化阶段
> **Status**: Draft
> **Version**: v2.0
> **Effective Date**: TBD
> **Scope**: 文档质量治理 / Pre-SSOT 准入门控 / 6 维度文档校验 / 纯 LLM Skill 架构
> **Owner**: 产品流程 / QA 治理 / 架构
> **Governance Kind**: NEW
> **Audience**: AI 实施代理、产品文档作者、Tech Lead、QA
> **Depends On**: ITERATION-DOCUMENT-CHECKLIST v2.1（§2.1 商业设计 + §二 Pre-SSOT 质量门 + PRD 可测性预审）
> **Supersedes**: 无

---

## 1. 背景

### 1.1 One-Sentence Summary

> **当前迭代流程缺少对"商业设计输入是否充分"的结构化校验机制——Pre-SSOT 文档的完整性完全依赖人工记忆检查，导致 SSOT 阶段频繁因输入不足而自由发挥，引发语义漂移、范围膨胀和设计意图丢失。**

### 1.2 现有能力与缺口

ITERATION-DOCUMENT-CHECKLIST v2.1 已定义 6 大维度的必输文档与必输要素（§2.1–§2.6），但存在以下执行缺口：

| 缺口 | 表现 | 后果 |
|------|------|------|
| **无自动化校验** | 检查清单是 Markdown 模板，人工逐项勾选，遗漏率高 | SSOT 启动时才发现缺失，被迫返工 |
| **无迭代类型区分逻辑** | 功能迭代 vs 商业迭代的边界模糊，执行者经常误判 | 商业迭代遗漏关键输入，功能迭代做了不必要的文档 |
| **Out of Scope 具体性无判定标准** | "本期不做微信支付"与"本期不做其他支付方式"都被勾选通过 | SSOT 仍需追问"这个做不做" |
| **成功指标可量化性无检验** | "提升用户体验"也被视为通过 | 测试设计无法从指标翻译出验证方法 |
| **质量门与详细检查脱节** | Q1–Q5 质量门与 §2.1–§2.6 逐项检查是两个独立环节 | 质量门通过但详细检查发现空洞内容 |

### 1.3 核心洞察

商业设计是整个迭代链条的"源头意图"。如果源头有缺陷（用户画像模糊、范围边界不具体、成功指标不可量化），后续所有 SSOT 形式化和 GSD 编码都会在此基础上放大偏差。

**关键原则**：校验技能不是"替代人类决策"，而是"在人类决策进入 SSOT 前，用结构化规则拦截不充分的输入"。

### 1.4 与现有技能的关系

| 技能 | 关系 | 说明 |
|------|------|------|
| `zeng-code-review-deep` | 上下游 | Design Check 在 SSOT 之前拦截文档缺陷；Deep Code Review 在编码阶段拦截代码缺陷 |
| `zeng-doc-quality-loop` | 平行互补 | Doc Quality Loop 侧重文档结构和可读性；Design Check 侧重业务设计输入的充分性与可形式化性 |
| `zeng-safe-code` | 无直接关系 | Safe Code 是安全扫描，Design Check 是流程门控 |

## 2. 问题

### 2.1 商业设计 6 大要素的缺失模式

根据 §2.1 定义，商业设计包含 6 个必输要素，每个要素有特定的缺失模式：

| # | 必输要素 | 常见缺失模式 | 缺失后果 |
|---|---------|-------------|---------|
| 1 | **迭代类型确认** | 未明确标注是功能迭代还是商业迭代 | SSOT 不知道该简化还是完整执行商业设计输入 |
| 2 | **用户画像** | 仅写"跑步爱好者"，无特征、场景、使用频率 | SSOT 无法判断功能优先级和交互复杂度 |
| 3 | **业务价值** | 仅写"提升用户体验"，无痛点、无不做代价 | SSOT 无法为功能排序，P0 划分无依据 |
| 4 | **范围边界** | Out of Scope 写"其他支付方式"（过于笼统）| SSOT 仍需追问具体边界，或擅自纳入遗漏内容 |
| 5 | **成功指标** | 写"DAU 提升 10%"但无测量方式和基准数据 | 测试设计无法定义验证标准 |
| 6 | **优先级** | 所有功能都标 P0，或无 P0 划分理由 | SSOT 拆解时资源分配无依据 |

### 2.2 质量门（Q1–Q5）的检查盲区

§二定义的 5 道质量门是"快速筛查"，但人工执行时存在盲区：

| 质量门 | 人工检查盲区 | 自动化可检测项 |
|--------|------------|---------------|
| Q1 文档存在性 | 文档存在但内容为空/占位符 | 文件存在 + 非空 + 非模板占位符 |
| Q2 决策可追溯性 | 决策有写但无依据说明 | 关键决策是否有"依据"关键词/链接 |
| Q3 异常覆盖度 | 写了"错误处理"但无具体错误码 | 异常流程是否有具体状态码/系统行为/用户感知 |
| Q4 可测试性 | AC 有写但无 Given-When-Then 结构 | AC 是否可通过语法模式匹配 |
| Q5 一致性 | 不同文档间数值矛盾 | 跨文档阈值/指标数值一致性校验 |

### 2.3 PRD 可测性预审（P1–P5）的执行时机

§二定义的 PRD 可测性预审在"PRD 定稿后、进入 Pre-SSOT 详细检查前"执行，但当前流程中：
1. 预审与详细检查混在一起，没有明确的阶段分割
2. 预审结果没有结构化记录，无法追溯
3. 不通过的 PRD 退回后缺乏重新提交机制

## 3. 决策

### 3.1 总体决策

引入 **`zeng-design-check`** 技能（Design Check Skill），作为 Pre-SSOT 阶段的结构化文档校验门控。采用 **纯 LLM + 结构化输出** 架构。

**架构选型决策**：Python 脚本层（scanner.py / reporter.py / 编排引擎 / 插件协议 / JSON 衔接）为解决"LLM 偶尔在确定性检查上不准确"的问题引入了大量复杂度（3 个 Python 文件 + 2 个 JSON schema + 插件加载协议），但实际准确率提升仅 ~2%。**去掉 Python 层**，将所有检查（包括确定性检查）交由 LLM 执行，通过结构化输出约束保证质量。

核心设计：

```text
┌─────────────────────────────────────────────────────────────┐
│           纯 LLM + 结构化输出 架构                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  LLM Agent（单一执行者）                                      │
│  ────────────────────                                       │
│  1. 读取输入文档                                             │
│  2. 按 Rubric 逐项校验（G1–G5 → BD/UX/AD/TD/EI → XC）       │
│  3. 输出结构化 JSON（每项: check_id + status + evidence）     │
│  4. 输出人可读 Markdown 报告                                  │
│                                                             │
│  域知识内嵌于 Prompt                                          │
│  ────────────────────                                       │
│  domains/business-design/rubric.md  → 内嵌到 Prompt          │
│  domains/product-design/rubric.md   → 内嵌到 Prompt          │
│  domains/ux-design/rubric.md        → 内嵌到 Prompt          │
│  domains/architecture/rubric.md     → 内嵌到 Prompt          │
│  domains/test-design/rubric.md      → 内嵌到 Prompt          │
│  domains/engineering/rubric.md      → 内嵌到 Prompt          │
│  cross-dimension/rubric.md          → 内嵌到 Prompt          │
│                                                             │
│  输入: 文档路径（单个/多个/目录）                               │
│  输出: design-check.json + design-check-report.md            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**为什么不用 Python 脚本层**：

| 之前（混合架构） | 现在（纯 LLM） | 变化 |
|----------------|---------------|------|
| scanner.py + reporter.py + run.py | 无 | -3 个 Python 文件 |
| document-scan.json → LLM → semantic-results.json → Python 合并 | LLM 直接输出 JSON + Markdown | -2 个 JSON schema |
| 插件加载协议（domain_config.json） | 域知识内嵌于 Prompt | -1 个协议 |
| 插件化目录结构（6 个 python_checks.py + 6 个 llm_rubric.md） | 7 个 rubric.md 文件 | -6 个 Python 文件 |
| Python↔LLM 衔接调试 | 无衔接，LLM 端到端 | 简化调试 |

**省下的复杂度**：9 个 Python 文件 + 2 个 JSON schema + 1 个插件协议 + 衔接调试成本。换来的是：确定性检查准确率从 100% 降到 ~98%（LLM 偶尔数错），Token 成本略高（~8K vs ~4K）。**这个交换是值得的**——2% 的准确率差异可通过 Prompt 中的"请逐项计数并输出数字"约束来缓解。

关键原则：
1. **只检不改**：校验技能只产出诊断报告，不修改文档内容
2. **结构化输出**：每个检查项输出 check_id + status(PASS/WARN/BLOCK) + evidence + suggestion
3. **MAC 驱动**：使用 ITERATION-DOCUMENT-CHECKLIST 定义的 Minimum Acceptable Criteria 作为判定阈值
4. **分阶段执行**：先质量门（快速筛查，任一 BLOCK 则停止），再域检查，再跨维度一致性
5. **Prompt 即配置**：域的 Rubric 直接写在 Prompt 中，无需额外配置文件

### 3.1.4 输入模型（Input Model）

校验的输入粒度决定了可执行的检查范围。核心规则：**域检查需要对应文档，跨维度检查需要多文档**。

#### 输入模式

| 模式 | 输入 | 可执行的检查 | 不可执行的检查 |
|------|------|------------|--------------|
| **单文档** | 1 个文件（如 PRD） | 通用质量门 G1–G5 + 该文档对应的域检查 | 跨维度一致性 XC（数据不足） |
| **多文档** | 2+ 个不同域的文件 | 通用质量门 G1–G5 + 各域检查 + 跨维度一致性 XC | 无（全量检查） |
| **目录扫描** | `--dir docs/` | 自动发现所有文档，等同多文档模式 | 无 |

#### 文档→域映射规则

输入文档通过文件路径/内容自动识别所属域：

| 文档特征 | 识别规则 | 映射到域 |
|---------|---------|---------|
| PRD（含用户故事、AC、业务规则） | 路径含 `prd/` 或内容含 `US-`/`AC`/`用户故事` | D1 商业设计 + D2 产品设计 |
| UX 规格说明书 | 路径含 `ux/` 或内容含 `设计原则`/`交互流程`/`设计令牌` | D3 UX 设计 |
| Tech Design（含 API、数据流、时序图） | 路径含 `tech/` 或内容含 `API`/`时序图`/`同步.*异步` | D4 架构设计 |
| TESTSET 文档 | 路径含 `testset/` 或内容含 `测试范围`/`Happy Path`/`边界条件` | D5 测试设计 |
| 实施范围声明 | 内容含 `实施范围`/`涉及模块`/`关键决策` | D6 工程实施 |
| 产品愿景/简报 | 路径含 `PROJECT.md` 或内容含 `产品定位`/`目标用户`/`核心价值` | D1 商业设计 |

#### 跨维度检查触发条件

XC 检查项的触发取决于相关域的产物是否存在：

| XC 检查项 | 需要的域产物 | 触发条件 |
|----------|------------|---------|
| XC-1 指标 ↔ AC 对齐 | D1 的成功指标 + D2 的 AC | D1 和 D2 均有产物 |
| XC-2 范围 ↔ 用户故事对齐 | D1 的 Out of Scope + D2 的用户故事 | D1 和 D2 均有产物 |
| XC-3 优先级 ↔ AC 对齐 | D1 的优先级 + D2 的 AC | D1 和 D2 均有产物 |
| XC-4 Out of Scope ↔ Feature | D1 的 Out of Scope + D2 的 Feature | D1 和 D2 均有产物 |
| XC-5 AC ↔ 测试用例对齐 | D2 的 AC + D5 的测试用例 | D2 和 D5 均有产物 |
| XC-6 API 契约 ↔ 技术设计 | D4 的 API + D5 的测试 | D4 和 D5 均有产物 |
| XC-7 UX 交互 ↔ 产品流程 | D2 的流程 + D3 的交互 | D2 和 D3 均有产物 |
| XC-8 实施范围 ↔ 架构分层 | D4 的分层 + D6 的范围 | D4 和 D6 均有产物 |

**规则**：XC 检查项缺少任一相关域产物时，该项标记为 `SKIPPED`（原因：`missing_domain:{domain_id}`），不计入 BLOCK/WARN 统计。

#### 最小可用输入

| 场景 | 最小输入 | 可产出 |
|------|---------|--------|
| **快速筛查** | 任意 1 个文档 | 通用质量门 + 该域检查 |
| **Pre-SSOT 准入** | PRD + 产品愿景 | D1 + D2 + XC-1–4 |
| **全量校验** | PRD + UX Spec + Tech Design + TESTSET | D1–D6 + XC-1–8 |

### 3.2 校验维度矩阵（6 域 + 跨维度）

基于 ITERATION-DOCUMENT-CHECKLIST v2.1 的 6 大维度（§2.1–§2.6），定义 **6 个领域 + 1 个跨维度层**的校验结构。每个领域包含独立的 Check ID 前缀、Rubric 和 MAC 标准。

#### 领域总览

| 域 ID | 域名称 | Checklist 章节 | Check ID 前缀 | 必输文档 | 状态 |
|-------|--------|---------------|---------------|---------|------|
| **D1** | 商业设计 | §2.1 | `BD-*` | 产品愿景、范围声明、成功指标 | **v2.0 已实现** |
| **D2** | 产品设计 | §2.2 | `PD-*` | PRD、用户旅程地图 | **v2.0 已实现** |
| **D3** | UX 设计 | §2.3 | `UX-*` | UX 规格说明书、用户旅程原型 | **v2.0 已实现** |
| **D4** | 架构设计 | §2.4 | `AD-*` | 技术架构总览、Tech Design 草案 | **v2.0 已实现** |
| **D5** | 测试设计 | §2.5 | `TD-*` | AC、风险场景清单、TESTSET 文档 | **v2.0 已实现** |
| **D6** | 工程实施 | §2.6 | `EI-*` | 实施范围声明、关键决策记录 | **v2.0 已实现** |
| **XC** | 跨维度一致性 | §4.1 | `XC-*` | （引用各域产物） | **v2.0 已实现** |

#### Layer 0: 通用质量门（Gate Check）— 所有域共享

| Gate ID | 检查项 | 校验规则 | 判定标准 |
|---------|--------|---------|---------|
| **G1** | 文档存在性 | 必输文档至少各有 1 份 | 文件存在 + 非空 + 非模板占位符 |
| **G2** | 决策可追溯性 | 关键决策有依据说明 | 含"依据"/"基于"/"参考"或标注"暂定" |
| **G3** | 异常覆盖度 | 异常流程含三层结构 | 错误码 + 系统行为 + 用户感知 |
| **G4** | 可测试性 | AC 有 GWT 或可观察指标 | 至少 1 条通过模式匹配 |
| **G5** | 一致性 | 跨文档概念一致 | 术语和数值匹配 |

#### D1: 商业设计检查项（v1.0 已定义）

| Check ID | 检查项 | MAC 标准 |
|----------|--------|---------|
| **BD-1** | 迭代类型确认 | 二选一明确标注 |
| **BD-2** | 用户画像 | 商业迭代必填；功能迭代标注复用 |
| **BD-3** | 业务价值 | 至少 1 个痛点 + 1 个不做代价 |
| **BD-4** | 范围边界 | Out of Scope ≥ 3 项，每项可独立判断 |
| **BD-5** | 成功指标 | 可量化 + 目标值 + 测量方式 + 基准 |
| **BD-6** | 优先级 | P0 ≤ 3，每个有"不做就失败"理由 |

#### D2: 产品设计检查项（计划）

| Check ID | 检查项 | MAC 标准 |
|----------|--------|---------|
| **PD-1** | 问题陈述 | 有背景 + 痛点 + 根本原因 |
| **PD-2** | 用户故事完整性 | US-XXX 编号 + AS A/I WANT/SO THAT 格式 |
| **PD-3** | AC 可测性 | 每条 AC 通过可测三问 |
| **PD-4** | 业务规则完整性 | 公式/阈值/频率/Guardrail 均有定义 |
| **PD-5** | 异常流程覆盖 | 业务异常 + 系统异常两层均有 |
| **PD-6** | 状态转换 | 状态图完整，转换条件明确 |
| **PD-7** | 前后端交互场景 | 场景清单完整，含同步/异步标注 |

#### D3: UX 设计检查项（计划）

| Check ID | 检查项 | MAC 标准 |
|----------|--------|---------|
| **UX-1** | 设计原则 | ≥ 3 条，每条有说明 + 示例 |
| **UX-2** | 核心页面交互流程 | 页面跳转 + 关键交互点完整 |
| **UX-3** | 状态表达规则 | 等级/计算/颜色/图标映射完整 |
| **UX-4** | 设计令牌引用 | 明确引用现有或新增令牌 |
| **UX-5** | 文案风格指南 | 口吻 + 禁忌词 + ≥ 3 个微文案示例 |
| **UX-6** | 平台差异策略 | H5 vs 小程序功能/交互/权限差异 |
| **UX-7** | 错误状态 UX | 异常展示方式 + 文案风格 |

#### D4: 架构设计检查项（计划）

| Check ID | 检查项 | MAC 标准 |
|----------|--------|---------|
| **AD-1** | 技术选型声明 | 语言/框架/DB/AI Provider 已确定 |
| **AD-2** | 架构分层 | 各层职责及文件位置明确 |
| **AD-3** | 同步/异步策略 | 每个外部调用标注同步/异步 + 理由 |
| **AD-4** | 核心数据流 | 入口→出口完整链路 + 转换点 + 缓存 |
| **AD-5** | 粗略 API 契约 | 端点+方法+核心字段+类型+必填 |
| **AD-6** | 时序图 | Mermaid/PlantUML，含同步/异步/超时/重试/降级/幂等 |
| **AD-7** | 存储方案 | 关系型/文档型+关键实体+JSONB vs 规范化 |
| **AD-8** | 非功能性需求 | 性能/安全/并发/降级，与时序图自洽 |
| **AD-9** | 集成点与外部依赖 | 外部服务+回调+fallback |

#### D5: 测试设计检查项（计划）

| Check ID | 检查项 | MAC 标准 |
|----------|--------|---------|
| **TD-1** | AC 可测试性 | Given-When-Then + 可测三问通过 |
| **TD-2** | Happy Path | 核心用户流端到端路径完整 |
| **TD-3** | 边界条件 | 每个核心字段至少 1 个边界条件 |
| **TD-4** | AI 不确定性场景 | 至少"AI 完全失败"+"格式异常"两种 |
| **TD-5** | 测试分层策略 | 5 层覆盖（单元/集成/E2E/性能/契约）|
| **TD-6** | Mock 数据需求 | fixture 用户 + 辅助数据 + 外部 Mock |
| **TD-7** | 测试执行检查清单 | 含状态机/降级/性能三类必检项 |
| **TD-8** | TESTSET 文档 | 9 节标准结构完整 |

#### D6: 工程实施检查项（计划）

| Check ID | 检查项 | MAC 标准 |
|----------|--------|---------|
| **EI-1** | 实施范围边界 | 精确到目录级 + ≥ 3 个修改文件类型 |
| **EI-2** | 关键实现决策 | 同步/异步、锁策略、缓存等已拍板 |
| **EI-3** | 依赖关系 | 前置 Phase/Feature/PR 已明确 |
| **EI-4** | 回滚与降级策略 | 回滚步骤 + 降级方案明确 |
| **EI-5** | 性能与容量预估 | 数据量/QPS/Token 消耗/存储增长 |

#### XC: 跨维度一致性检查项（计划）

| Check ID | 检查项 | 引用域 |
|----------|--------|--------|
| **XC-1** | 指标 ↔ AC 对齐 | D1 + D2 |
| **XC-2** | 范围 ↔ 用户故事对齐 | D1 + D2 |
| **XC-3** | 优先级 ↔ AC 对齐 | D1 + D2 |
| **XC-4** | Out of Scope ↔ Feature 对齐 | D1 + D2 |
| **XC-5** | AC ↔ 测试用例对齐 | D2 + D5 |
| **XC-6** | API 契约 ↔ 技术设计对齐 | D4 + D5 |
| **XC-7** | UX 交互 ↔ 产品流程对齐 | D2 + D3 |
| **XC-8** | 实施范围 ↔ 架构分层对齐 | D4 + D6 |

### 3.3 校验严重级别

| 级别 | 含义 | 后果 |
|------|------|------|
| **BLOCK** | 必输要素缺失或严重不合格 | 阻塞进入 SSOT，必须补充后重新提交 |
| **WARN** | 要素存在但质量不足（如 Out of Scope 不够具体） | 建议补充，不阻塞但标记风险 |
| **PASS** | 要素完整且达到 MAC 标准 | 通过 |
| **N/A** | 功能迭代中可复用的要素 | 标注复用来源 |

### 3.4 执行流程（纯 LLM）

```
阶段 1: 文档读取与上下文构建 [Skill Prompt]
    │
    ├── 读取输入文档路径（单个/多个/目录扫描）
    ├── 读取文档内容
    ├── 确定文档→域映射（路径关键词 + 内容特征）
    ├── 构建 LLM 上下文：文档内容 + 对应域 Rubric
    │
    ▼
阶段 2: 通用质量门 — G1–G5 [LLM]
    │
    ├── 按 Rubric 逐项校验
    ├── 判定: 任一 BLOCK → 停止，输出缺失项清单
    │
    ▼
阶段 3: 领域检查 — 按域逐项校验 [LLM]
    │
    ├── 对每个已识别的域:
    │   ├── 内嵌该域的 Rubric 到 Prompt
    │   ├── 按 Rubric 逐项检查
    │   └── 输出该域的检查结果（check_id + status + evidence）
    │
    ├── 判定: 任一域有 BLOCK → 记录但继续其他域（不互相阻塞）
    │
    ▼
阶段 4: 跨维度一致性 — XC [LLM]（仅多文档模式）
    │
    ├── 从各域结果中提取指标/故事/AC/Feature/Scope 列表
    ├── 按 cross-dimension/rubric.md 做语义对齐
    │
    ▼
阶段 5: 结构化输出 [LLM]
    │
    ├── 输出 design-check.json（结构化检查结果）
    ├── 输出 design-check-report.md（人可读报告）
    │
    ▼
阶段 6: 人工确认 [Human]
    │
    ├── 展示: 报告摘要（按域分组）
    ├── 输入: 用户确认或补充
    └── 输出: design-check-verdict.json
```

## 4. 术语定义

| 术语 | 定义 |
|------|------|
| **Design Check Skill** | Pre-SSOT 阶段的 6 大维度文档校验技能，采用纯 LLM + 结构化输出架构 |
| **域 Rubric** | 每个校验维度的检查规则定义，内嵌于 LLM Prompt 中 |
| **MAC (Minimum Acceptable Criteria)** | 每个必输要素的最低可接受标准，达到即视为"已拍板" |
| **质量门 (Gate)** | 快速筛查机制，任一不通过则停止详细检查 |
| **迭代类型** | 功能迭代（现有框架内增改）vs 商业迭代（涉及收费/权限/合规/核心数据模型变更） |
| **BLOCK** | 阻塞级别，必须补充后才能进入 SSOT |
| **语义漂移** | SSOT 阶段因输入不足而自由发挥，导致产出偏离原始设计意图 |

## 5. 校验规则详细定义（Rubric）

### 5.1 质量门 Rubric

#### G1 — 文档存在性

| 检查项 | PASS 条件 | FAIL 条件 |
|--------|----------|----------|
| 必输文档存在 | 文件存在 + 大小 > 100 字节 | 文件不存在或大小 < 100 字节 |
| 非空内容 | 不含 `TODO`/`TBD`/`占位`/`待补充` 占位符 | 含占位符 |
| 结构完整 | 至少包含 3 个二级标题 | 结构缺失 |

#### G2 — 决策可追溯性

| 检查项 | PASS 条件 | FAIL 条件 |
|--------|----------|----------|
| 决策有依据 | 包含"依据"/"基于"/"参考"/"数据表明" | 无任何依据说明 |
| 明确暂定 | 标注"产品决策暂定，上线后根据数据调整" | 既无依据也未标注暂定 |

#### G3 — 异常覆盖度

| 检查项 | PASS 条件 | FAIL 条件 |
|--------|----------|----------|
| 错误码/状态 | 有具体错误码或状态描述 | 仅写"错误处理"无细节 |
| 系统行为 | 有系统行为描述 | 缺失 |
| 用户感知 | 有用户端展示/反馈描述 | 缺失 |

#### G4 — 可测试性

| 检查项 | PASS 条件 | FAIL 条件 |
|--------|----------|----------|
| AC 结构 | 至少 1 条含 Given/When/Then 或可观察指标 | 全部 AC 无结构 |

#### G5 — 一致性

| 检查项 | PASS 条件 | FAIL 条件 |
|--------|----------|----------|
| 术语一致 | 同一概念在不同文档中名称一致 | 名称不同 |
| 数值一致 | 阈值/指标在不同文档中数值一致 | 数值不同 |

### 5.2 商业设计要素 Rubric

#### BD-1 — 迭代类型

| PASS | FAIL |
|------|------|
| 明确标注"功能迭代"或"商业迭代" | 未标注 |

#### BD-2 — 用户画像

| 迭代类型 | PASS 条件 | FAIL 条件 |
|---------|----------|----------|
| 商业迭代 | 有用户特征 + 使用场景 + 使用频率 | 任一缺失 |
| 功能迭代 | 标注"复用现有用户画像"并引用来源 | 未标注 |

#### BD-3 — 业务价值

| 迭代类型 | PASS 条件 | FAIL 条件 |
|---------|----------|----------|
| 商业迭代 | 有具体痛点描述 + 不做的代价 | 任一缺失 |
| 功能迭代 | 可简化为一句话价值陈述 | 完全缺失 |

#### BD-4 — 范围边界

| PASS 条件 | FAIL 条件 |
|----------|----------|
| Out of Scope ≥ 3 项 | Out of Scope < 3 项 |
| 每项具体到可独立判断 | 含笼统描述（"其他XX"、"类似功能"）|
| 不含模糊限定词 | 含"等"、"等等"、"其他"等模糊词 |

**具体性判定规则**：
- ✅ "本期不做微信支付" → 可独立判断
- ✅ "本期不支持离线模式" → 可独立判断
- ✅ "本期不做 iOS 端" → 可独立判断
- ❌ "本期不做其他支付方式" → 无法判断"其他"包含什么
- ❌ "本期不做类似功能" → 无法判断"类似"的边界

#### BD-5 — 成功指标

| PASS 条件 | FAIL 条件 |
|----------|----------|
| 至少 1 个可量化指标 | 无指标或指标不可量化 |
| 有目标值 | 无目标值 |
| 有测量方式 | 无测量方式 |
| 有基准数据或假设来源 | 无基准也未标注假设 |

**可量化性判定规则**：
- ✅ "DAU 提升 20%" → 可量化
- ✅ "用户满意度 NPS ≥ 40" → 可量化
- ❌ "提升用户体验" → 不可量化
- ❌ "提高用户活跃度" → 不可量化（无具体指标）

#### BD-6 — 优先级

| PASS 条件 | FAIL 条件 |
|----------|----------|
| 有 P0/P1/P2 划分 | 无优先级划分 |
| P0 不超过 3 个 | P0 > 3 个 |
| 每个 P0 有"不做就失败"理由 | P0 无理由 |

### 5.3 PRD 可测性预审 Rubric

#### P1 — AC 完整性

| PASS | FAIL |
|------|------|
| AC 数量 ≥ 用户故事数量 | 有用户故事无对应 AC |

#### P2 — 可测三问

| PASS 条件 | FAIL 条件 |
|----------|----------|
| AC 包含触发条件（怎么触发） | 缺少触发条件 |
| AC 包含判定标准（怎么判定通过） | 缺少判定标准 |

#### P3 — 时间具体化

| PASS 条件 | FAIL 条件 |
|----------|----------|
| 时间值为具体数值 | 时间值为"尽快"、"适当"等模糊词 |
| 或标注"见 Tech Design §X" | 无具体值也无引用 |

#### P4 — AI 输出模式

| PASS 条件 | FAIL 条件 |
|----------|----------|
| 涉及 AI 的 AC 有 JSON 结构/字段范围/枚举值 | 涉及 AI 但无输出描述 |
| 或标注"由技术方案确定" | 无描述也无引用 |

#### P5 — 阈值可追溯

| PASS 条件 | FAIL 条件 |
|----------|----------|
| 阈值附带数据来源 | 阈值无来源 |
| 或标注"产品决策暂定" | 无来源也未标注暂定 |

### 5.4 跨维度一致性 Rubric

#### XC-1 — 指标 ↔ AC 对齐

| PASS | FAIL |
|------|------|
| 每个成功指标至少有 1 条对应 AC | 有指标无对应 AC |

#### XC-2 — 范围 ↔ 用户故事对齐

| PASS | FAIL |
|------|------|
| In Scope 的每项内容至少有 1 条用户故事 | In Scope 内容无对应用户故事 |

#### XC-3 — 优先级 ↔ AC 对齐

| PASS | FAIL |
|------|------|
| P0 功能的所有 AC 均存在 | P0 功能有 AC 缺失 |

#### XC-4 — Out of Scope ↔ Feature 对齐

| PASS | FAIL |
|------|------|
| Out of Scope 内容未被任何 Feature 涵盖 | Out of Scope 内容被 Feature 涵盖 |

## 6. Consequences

### 6.1 正向影响

1. **全维度覆盖**：55 项检查覆盖 6 大维度 + 跨维度一致性，Pre-SSOT 输入质量全面可控
2. **SSOT 语义漂移减少**：源头输入充分后，SSOT 自由发挥的概率显著降低
3. **迭代类型差异化处理**：功能迭代与商业迭代的校验范围自动适配
4. **可追溯**：每次检查产出结构化 JSON + 人可读报告，支持事后审计
5. **与现有流程无缝衔接**：校验报告可直接作为 SSOT 启动的准入凭证
6. **架构极简**：纯 LLM 架构，无 Python 脚本层、无 JSON 衔接、无插件加载协议，维护成本最低
7. **渐进可扩展**：新增维度 = 新增 Rubric 文件 + Prompt 内嵌，核心逻辑不变
8. **确定性检查 Prompt 约束**：通过"请逐项计数并输出数字"等 Prompt 指令缓解 LLM 在确定性检查上的偶尔偏差

### 6.2 代价

1. **额外流程开销**：每次迭代增加 5–10 分钟的文档校验时间
2. **文档作者负担**：Out of Scope 具体化、成功指标可量化化等要求提高了文档撰写标准
3. **误报风险**：LLM 语义判断可能对自然语言描述产生误判
4. **维护成本**：校验规则需随 ITERATION-DOCUMENT-CHECKLIST 版本更新同步维护
5. **确定性检查准确率**：LLM 执行确定性检查（文件存在、计数、关键词匹配）偶尔有偏差（~2%），通过 Prompt 约束缓解
6. **Token 成本**：确定性检查也消耗 LLM Token（~8K vs 混合架构的 ~4K），但省去了 Python 层的开发维护成本

### 6.3 度量指标

| 指标 | 目标 | 度量方式 |
|------|------|---------|
| Pre-SSOT 一次通过率 | > 70% | 设计检查 PASS / 总检查次数 |
| SSOT 语义漂移率 | < 10% | SSOT 产出中发现的漂移项 / 总产出项 |
| 平均返工次数 | < 1.5 次 | 迭代从首次提交到通过的平均次数 |
| 校验覆盖率 | 100% | 已校验的必输要素 / 总必输要素 |

## 7. Rejected Alternatives

### 7.1 纯人工 Checklist 勾选

**拒绝**。人工勾选遗漏率高（实测 > 30%），无法保证一致性，且无结构化记录可供追溯。

### 7.2 与 zeng-doc-quality-loop 合并

**拒绝**。Doc Quality Loop 侧重文档结构、可读性、术语一致性等"文档质量"维度；Design Check 侧重业务设计输入的"充分性"和"可形式化性"。两者目标不同，合并会导致单个技能过于复杂。

### 7.3 SSOT 阶段事后校验

**拒绝**。事后校验意味着 SSOT 已经基于不充分的输入产出了形式化制品，返工成本是事前校验的 3–5 倍。事前拦截是更经济的策略。

### 7.4 不区分迭代类型

**拒绝**。功能迭代与商业迭代的输入要求差异显著（§2.1 按迭代类型区分），不区分会导致功能迭代做不必要的文档工作，或商业迭代遗漏关键输入。

### 7.5 纯 Python 实现

**拒绝**。23 项检查中有 11 项需要语义判断（如"Out of Scope 是否具体到可独立判断"、"成功指标是否可量化"），正则/规则无法可靠实现，实测误报率 > 50%。纯 Python 只能覆盖确定性检查（7 项），覆盖率仅 30%。

### 7.6 混合 Python+LLM 架构（v1.1 方案）

**拒绝**。v1.2 方案设计了 Python 脚本层（scanner.py / reporter.py / 编排引擎）+ LLM 语义层 + JSON 衔接 + 插件加载协议（domain_config.json），共 9 个 Python 文件 + 2 个 JSON schema + 1 个协议。实测发现：(1) Python 层带来的确定性检查准确率提升仅 ~2%（从 98% 到 100%），但引入了大量衔接调试成本；(2) 插件加载协议增加了新域的配置复杂度；(3) Python/LLM 之间的 JSON 衔接是调试热点。**这个交换不值得**——2% 的准确率差异可通过 Prompt 中的"请逐项计数并输出数字"约束来缓解，而省下的 9 个 Python 文件 + 1 个协议 + 衔接调试成本是显著的。

### 7.7 单体 Skill 内部扩展（6 维度写在一个大 Prompt 中）

**拒绝**。6 个维度的 Rubric、MAC、检查规则差异显著，全部写在一个 Prompt 中会导致 Prompt 膨胀（~5000 行），新增维度时修改 Prompt 风险高，不同维度耦合发布。域 Rubric 分文件管理，按需内嵌到 Prompt，解决了这些问题。
