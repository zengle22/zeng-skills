# 工程版本开发迭代 — 文档检查清单

> **用途**：界定人类决策（Pre-SSOT）与机械拆解（SSOT）的边界，防止 SSOT 阶段因输入不足而自由发挥导致语义漂移。
> **核心原则**：凡是需要人类反复讨论、拍板、确认的内容，都放在进入 SSOT 之前敲定。SSOT 只做结构化的补充、拆解与形式化，**不得改变业务意图**。
> **适用对象**：AI 助手（Claude / Cline / Codex / Qwen）及人类审核者。
> **更新频率**：随工作流演进同步更新。

---

## ⚡ AI 自检速查卡（5 秒版）

> **使用方式**：AI 在开始任何迭代前，先扫一眼这张速查卡。全部为 ✅ 则进入详细检查；任一 ❌ 则停止，查阅下方完整清单定位缺失项。

| # | 检查项 | 判断标准 |
|---|-------|---------|
| 1 | **有 PRD？** | 包含用户故事 + 验收标准（AC） |
| 2 | **有范围界定？** | 明确 In Scope / Out of Scope |
| 3 | **有业务规则？** | 含阈值 + 阈值来源说明 |
| 4 | **有异常流程？** | 覆盖业务异常 + 系统异常两层 |
| 5 | **有 UX 规格？** | 含设计原则 + 错误状态 UX 规范 |
| 6 | **有 Tech Design？** | 含同步/异步策略 + 分层职责 |
| 7 | **有 API 契约？** | 端点 + 核心字段 + 版本策略 |
| 8 | **有时序图？** | 如涉及前后端协作，必须有 Mermaid/PlantUML 时序图 |
| 9 | **有存储方案？** | 表结构思路 / JSONB vs 规范化 |
| 10 | **有测试策略？** | AC + 边界条件 + AI 不确定性场景 + 独立 TESTSET 文档（参考 TESTSET-M01 模板） |
| 11 | **有实施范围？** | 涉及模块 + 明确不碰的文件 |
| 12 | **已读规范？** | `AI_CONSTITUTION.md` + `AGENTS.md` + 当前模块 `docs/mvp-lite` 真源 |
| 13 | **Git 干净？** | 分支正确，无未提交改动 |

**速查结论**：全部 ✅ → 进入详细检查 & 编码；任一 ❌ → **停止**，定位缺失项并补充

### 核心边界规则

| 阶段 | 可以做什么 | **禁止做什么** |
|-----|-----------|--------------|
| **Pre-SSOT** | 讨论、辩论、修改、拍板、推翻重来 | 不得输出"最终形式化制品"（如精确字段、表结构、测试用例） |
| **SSOT** | 结构化、拆解、细化字段、补充边界条件、建立追溯关系 | **不得改变业务意图**（见下方红色警戒线） |
| **GSD** | 写代码、跑测试、调试、重构（在 SSOT 约束内） | 不得绕过 SSOT 产物中的设计决策；发现不可行时必须回退到 Pre-SSOT 重新决策 |

## 二、Pre-SSOT：人类意图输入（进入 SSOT 的门槛）

> **准入原则**：以下每个维度的"必输文档"和"必输要素"缺一不可。缺失任何一项，SSOT 必须**拒绝启动**，返回人类补充，而不是自行发挥填补。

---

### PRD 可测性预审（Pre-Pre-SSOT）

在 PRD 定稿后、进入 Pre-SSOT 详细检查前，由 QA 或 Tech Lead 对 PRD 的 AC 进行**可测性预审**。未通过预审的 PRD 应退回产品经理补充，不应进入 Pre-SSOT。

| # | 预审项 | 通过标准 | 不通过的处理 |
|---|-------|---------|------------|
| P1 | **AC 完整性** | 每条用户故事至少 1 条 AC | 退回补充 AC |
| P2 | **可测三问** | 每条 AC 能回答：① 测什么？② 怎么触发？③ 怎么判定通过？ | 退回重写 AC，补充触发条件和判定标准 |
| P3 | **时间具体化** | 涉及时间的 AC 有具体数值（或明确标注"由技术方案确定，见 Tech Design"） | 退回补充时间阈值 |
| P4 | **AI 输出模式** | 涉及 AI 的 AC 有期望输出模式（JSON 结构、字段范围、枚举值） | 退回补充 AI 期望输出 |
| P5 | **阈值可追溯** | 业务规则中的阈值有数据来源或假设说明 | 退回补充阈值来源 |

> **原则**：Pre-SSOT 检查发现 AC 不可测 = 浪费一轮时间。应在 PRD 阶段就拦截。

---

### Pre-SSOT 质量门（Pre-Gate）

在逐项检查 6 大维度之前，先运行以下**质量门**。质量门不通过，不要浪费时间进入详细检查——文档齐全但内容空洞同样会导致 SSOT 自由发挥。

| # | 质量门检查项 | 通过标准 | 不通过的后果 |
|---|------------|---------|------------|
| Q1 | **文档存在性** | 6 大维度的必输文档至少各有 1 份 | SSOT 无从参考，必然自由发挥 |
| Q2 | **决策可追溯性** | 文档中的关键决策（技术选型、阈值、范围）**必须有依据**（数据、用户研究、竞品分析、或明确标注为"产品决策暂定"） | SSOT 无法判断决策是否可靠，可能质疑或误改 |
| Q3 | **异常覆盖度** | 异常流程不仅写了"错误处理"，还明确列出**具体错误码/状态 + 系统行为 + 用户感知** | SSOT 会补全为"合理"的默认值，导致与实际意图不符 |
| Q4 | **可测试性** | 每条用户故事的 AC 能被第三方独立验证（有 Given-When-Then 或可观察的指标） | 测试设计无法从 AC 翻译，SSOT 会自行定义"通过标准" |
| Q5 | **一致性** | 同一概念在不同文档中名称一致、数值一致、逻辑不矛盾 | SSOT 会选择其中一份文档为准，导致另一份被覆盖 |

> **最小可接受标准（MAC）定义**：每条必输要素后面标注的 **MAC** 表示"AI 判断该要素是否足够好的最低标准"。达到 MAC 即视为"已拍板"，不达到即视为"仍需人类补充"。

### 2.1 商业设计（Business Design）

**回答**："为什么做、为谁做、值不值得做、边界在哪里"

#### 必输文档

| # | 文档 | 典型路径 | 作用 |
|---|------|---------|------|
| 1.1 | **产品愿景 / 产品简报** | `docs/prd/`、`PROJECT.md`、或 `_bmad-output/planning-artifacts/` | 明确产品定位、目标用户、核心价值主张 |
| 1.2 | **需求范围声明** | PRD「范围界定」章节 | 明确 **In Scope**（本次必须做）与 **Out of Scope**（明确不做，防止后期膨胀） |
| 1.3 | **成功指标** | PRD「目标与成功指标」章节 | 可量化的北极星指标及测量方式 |

#### 必输要素（这些 SSOT 不能猜）

**按迭代类型区分：**

| 迭代类型 | 判断标准 | 商业设计必输要求 |
|---------|---------|----------------|
| **功能迭代** | 在现有产品框架内增加/修改功能，不涉及商业模式变化，**且不涉及核心数据模型变更** | 只需确认：① 本次迭代是否改变成功指标或用户画像（如否，可复用现有）；② 本次迭代的范围边界 |
| **商业迭代** | 涉及收费模式、用户权限体系、合规要求、目标用户变更，**或涉及核心数据模型变更** | 需要完整的商业设计输入：用户画像、业务价值、范围边界、成功指标、优先级 |

- [ ] **迭代类型确认**：本次迭代属于功能迭代还是商业迭代？
- [ ] **用户画像**（商业迭代必填 / 功能迭代复用现有）：主要用户是谁、有什么特征、使用场景是什么
- [ ] **业务价值**（商业迭代必填 / 功能迭代可简化）：这个功能解决什么痛点、不做的代价是什么
- [ ] **范围边界**：列出至少 3 项"明确不做"的内容，防止 SSOT 擅自扩展
  > **MAC**：Out of Scope 清单中的每一项都具体可判断（如"本期不做微信支付"✓，"本期不做其他支付方式"✗）
- [ ] **成功指标**（商业迭代必填 / 功能迭代可选）：至少 1 个可量化的指标 + 目标值 + 测量方式
  > **MAC**：指标可以被独立验证，目标值有基准或假设来源
- [ ] **优先级**（商业迭代必填 / 功能迭代复用现有）：P0/P1/P2 划分，SSOT 拆解时据此分配资源
  > **MAC**：P0 项不超过 3 个，且每项都有明确的"不做就失败"理由

#### 验收标准（什么算"足够好"）

> SSOT 能从中直接提取商业价值语句，**不需要问"用户是谁"、"为什么做这个功能"**。

### 2.2 产品设计（Product Design）

**回答**："做什么、用户怎么用、核心流程是什么、异常怎么办"

#### 必输文档

| # | 文档 | 典型路径 | 作用 |
|---|------|---------|------|
| 2.1 | **PRD（产品需求文档）** | `docs/mvp-lite/prds/` | 完整的问题陈述、用户故事、范围、业务规则 |
| 2.2 | **用户旅程地图 / 用户故事地图** | `docs/mvp-lite/ux/`、`docs/mvp-lite/ux-prototypes/` | 可视化用户从起点到终点的完整路径 |

#### 必输要素（PRD 中必须包含的章节）

- [ ] **问题陈述**：背景、痛点、根本原因分析（Why）
- [ ] **用户故事**：格式 `AS A... I WANT... SO THAT...`，编号 US-XXX，**每条必须有验收标准（AC）**
  > **MAC**：每个故事都有 AC，且 AC 能被第三方独立验证（有 Given-When-Then 或可观察指标）
- [ ] **范围界定**：In Scope / Out of Scope 清单，**Out of Scope 必须具体**
  > **MAC**：Out of Scope 中的每一项都具体到 SSOT 不需要问"这个做不做"
- [ ] **业务规则**：计算逻辑、公式、阈值参数、频率限制、Guardrail 规则。**每个阈值必须附带数据来源或假设说明**（如："基于历史用户数据 95 分位"、"产品决策暂定，上线后根据数据调整"）
  > **MAC**：所有阈值都有来源说明；Guardrail 规则明确"触发条件 + 限制动作 + 异常处理"
- [ ] **异常流程**：错误场景、降级路径、超时处理、重试策略、空状态/加载状态/失败状态。**必须覆盖两个层面**：
  - **业务层面**：用户做了什么不该做的（如：重复提交、越权操作、数据格式错误）
  - **系统层面**：服务故障（如：AI 超时、网络断开、数据库锁冲突、Redis 宕机）
  > **MAC**：每个核心场景至少有一个业务异常 + 一个系统异常被定义；每个异常都有"系统行为 + 用户感知"
- [ ] **状态转换**：数据/页面/流程的状态变化条件（如：draft → active → paused → completed）
- [ ] **前后端交互场景清单**：涉及前后端协作的核心场景列表（如：提交反馈 → AI 异步调整 → 前端轮询/推送更新）。**仅列场景，不涉及具体技术时序**

#### 必输要素（用户旅程地图中必须包含）

- [ ] **Happy Path**：正常完成核心目标的最短路径
- [ ] **分支流程**：条件判断后的不同路径（如：已登录 vs 未登录、有风险 vs 无风险）
- [ ] **异常分支**：网络失败、AI 服务失败、用户取消、权限不足、数据不存在
- [ ] **状态转换图**：页面或组件的关键状态及转换条件

#### 验收标准

> SSOT 不需要问"这个按钮点击后应该跳到哪"、"这个场景要不要处理"，所有流程和规则已明确。

### 2.3 UX 设计（User Experience Design）

**回答**："界面遵循什么原则、怎么交互、状态怎么表达、文案什么口吻"

#### 必输文档

| # | 文档 | 典型路径 | 作用 |
|---|------|---------|------|
| 3.1 | **UX 规格说明书** | `docs/ux/*-ux-spec.md` | 设计原则、页面规格、组件规格、交互细节、文案规范 |
| 3.2 | **用户旅程原型**（与 2.2 共享） | `.artifacts/*-journey-prototype.md` | 交互流程、页面跳转、反馈机制 |

#### 必输要素

- [ ] **设计原则**：至少 3-5 条核心原则（如：透明不解释、零摩擦自动生效、可追溯、教练口吻、渐进披露）
  > **MAC**：每条原则都有"说明 + 体现示例"（如"透明不解释：展示调整原因但不展示算法逻辑"）
- [ ] **核心页面交互流程**：页面跳转图、关键交互点（点击/滑动/长按的行为定义）
- [ ] **状态表达规则**（如涉及状态系统）：状态等级定义、计算规则、颜色/图标/文案映射
- [ ] **设计令牌引用**：明确引用现有 `variables.scss` 还是新增令牌；如新增，需列出新增令牌及值
- [ ] **文案风格指南**：口吻（第一人称/关怀式/命令式）、禁忌词、微文案示例（至少 3 个场景的文案示例）
  > **MAC**：3 个示例覆盖"正常状态、警告状态、错误状态"三种语境，且风格一致
- [ ] **平台差异策略**：H5 与微信小程序的功能差异、交互差异（如：小程序有 pull-down-refresh，H5 没有）、权限差异（如：蓝牙/GPS 在两端的不同表现）、安全区域适配
- [ ] **错误状态 UX 规范**：每种系统异常对应的前端展示方式（toast / 空状态页 / 骨架屏 / 降级内容 / 重试按钮），以及对应的文案风格

#### 验收标准

> SSOT 不需要发明设计原则、不需要选择颜色、不需要决定"这里用弹窗还是底部 Sheet"。所有设计决策已拍板，SSOT 只需细化为组件参数。

### 2.4 架构设计（Architecture Design）

**回答**："技术怎么实现、分层怎么划、同步还是异步、数据怎么存"

#### 必输文档

| # | 文档 | 典型路径 | 作用 |
|---|------|---------|------|
| 4.1 | **技术架构总览** | `docs/mvp-lite/arch/` | 系统分层、数据流、关键抽象、文件位置映射 |
| 4.2 | **技术设计草案 / Rough Tech Design** | `docs/mvp-lite/tech/` | 粗略的数据流、组件职责、存储思路、API 草案 |

#### 必输要素

- [ ] **技术选型声明**：语言版本、框架、数据库、AI Provider、关键第三方库（**已确定，不再讨论**）
- [ ] **架构分层与职责边界**：Transport / Handler / Service / AI / Repository / Domain 各层职责及文件位置
- [ ] **同步/异步策略**：哪些调用同步、哪些异步（如：AI 生成是异步 goroutine、反馈提交是同步 200 + 异步处理）
  > **MAC**：每个涉及外部调用（AI/数据库/第三方服务）的场景都明确标注同步或异步，并说明理由
- [ ] **核心数据流**：请求从入口到出口的完整链路、数据转换点、缓存策略
- [ ] **粗略 API 契约**：端点列表（路径+方法）、核心请求/响应字段（名称+类型+是否必填）、版本策略、鉴权方式
  > **MAC**：每个端点都有路径+方法；核心字段有名称+类型+是否必填；新增端点与现有端点版本一致
- [ ] **前后端交互时序图**（如涉及前后端协作）：**必须使用 Mermaid 或 PlantUML 格式**。每张时序图必须标注：
  - **调用方向**：谁调谁（前端→后端、后端→AI Service、后端→数据库）
  - **同步/异步**：每次调用的性质
  - **超时时间**：每次调用的超时阈值
  - **重试次数**：失败时重试几次、重试间隔策略
  - **降级路径**：某一步失败后系统如何继续（如：AI 失败时返回规则引擎结果、返回错误码让前端展示兜底文案）
  - **幂等性策略**：重复调用是否安全、如何防重
  > **MAC**：至少覆盖 Happy Path 的完整时序 + 1 个关键异常时序；使用 Mermaid 或 PlantUML 语法，可被 SSOT 直接解析
- [ ] **存储方案思路**：关系型 vs 文档型、关键实体、JSONB vs 规范化、是否需要新表/新字段
- [ ] **非功能性需求**：性能目标（P99 延迟）、安全要求（鉴权/脱敏）、并发约束、降级策略。**必须与前后端交互时序图中的超时时间自洽**（如：API P99 目标 2s，则时序图中单步调用超时不能设为 30s 且无说明）
- [ ] **集成点与外部依赖**：需要调用的外部服务、回调机制、失败时的 fallback 策略

#### 验收标准

> SSOT 不需要做技术选型、不需要决定"这个功能用同步还是异步"、不需要选择"用 PostgreSQL 还是 MongoDB"。所有技术决策已拍板，SSOT 只需细化接口字段和表结构。

### 2.5 测试设计（Test Design）

**回答**："怎么验证正确性、关键路径是什么、已知风险有哪些"

#### 必输文档

| # | 文档 | 典型路径 | 作用 |
|---|------|---------|------|
| 5.1 | **验收标准（AC）** | PRD「用户故事」章节 | 每条用户故事的可测试验收条件 |
| 5.2 | **已知风险场景清单** | PRD「异常流程」+ Tech Design「非功能性需求」 | 边界条件、并发问题、AI 不确定性、网络抖动 |

#### 必输文档（TESTSET 标准结构）

每个模块的独立测试策略文档（`TESTSET-{Module}.md`）必须包含以下 9 个标准章节。`docs/mvp-lite/testset/TESTSET-M01-Today-Card.md` 为规范模板。

| # | 标准章节 | 说明 |
|---|---------|------|
| 1 | **测试范围** | In Scope / Out of Scope 清单，明确本模块负责验证的边界 |
| 2 | **Happy Path 端到端测试** | 核心用户流的完整端到端路径，每条 Happy Path 引用对应 AC |
| 3 | **边界条件测试** | 空值、极值、超长字符串、并发请求、大数据量、时区/日期边界 |
| 4 | **状态机边界测试** | 如模块涉及状态转换，必须列出所有状态迁移的测试用例 |
| 5 | **AI 不确定性场景** | 如模块涉及 AI 调用；纯规则模块标注 **N/A** 并说明理由 |
| 6 | **测试分层策略** | 各层测试的范围、工具、数量预估、关键覆盖点 |
| 7 | **可测性评审结论** | 逐条评价 PRD 中 AC 的可测性，标记可直接翻译 / 需要补充 / 不在本模块范围 |
| 8 | **Mock 数据需求** | 测试所需的 fixture 数据清单，含用户状态、辅助数据、外部服务 Mock 要求 |
| 9 | **测试执行检查清单** | 可勾选的验收项，用于开发自测和 QA 验收 |

> **MAC**：`TESTSET` 文档必须在技术实现开始前完成，作为开发自测和 QA 验收的 SSOT。

#### 必输要素

- [ ] **可测试的 AC**：每条用户故事至少 1 条 AC，格式 `Given... When... Then...`，**必须可自动化验证或人工验证**。
  > **每条 AC 必须通过"可测三问"**：
  > 1. **测什么？** 验证的具体行为或结果是什么？
  > 2. **怎么触发？** 通过什么操作/输入可以到达这个状态？
  > 3. **怎么判定通过？** 观察什么输出/数据/状态变化来确认？
  > **MAC**：AC 中的 Then 子句能被独立观察（有数据变化、有 API 返回值、有 UI 状态变化）；涉及时间的必须有具体数值（或明确标注"由技术方案确定，见 Tech Design"）；涉及 AI 的必须有"期望输出模式"（JSON 结构、字段范围、枚举值）
- [ ] **关键路径（Happy Path）**：核心用户流必须能跑通的端到端路径
- [ ] **边界条件**：空值、极值、超长字符串、并发请求、大数据量
  > **MAC**：每个核心业务字段至少有一个边界条件被定义
- [ ] **AI 不确定性场景**：AI 返回无效 JSON、AI 超时、AI 返回内容与预期不符、Token 超限
  > **MAC**：至少定义"AI 完全失败"和"AI 返回格式异常"两种场景的系统行为
- [ ] **测试分层策略**：明确以下五类测试的覆盖范围与工具选型
  - **单元测试** — 独立函数、组件、工具类（如 go-sqlmock）
  - **集成测试** — 完整 API 链路、数据库事务、外部服务交互（如 PostgreSQL + Redis）
  - **E2E 测试** — 前端状态切换与关键用户交互（如 Playwright）
  - **性能测试** — 响应时间、并发负载、资源消耗（如 k6 / Go benchmark）
  - **契约测试** — API 响应 Schema 兼容性、字段严格匹配（如 schemathesis / 手动断言）
  > **MAC**：每个模块至少定义单元测试和集成测试的覆盖范围；涉及前端交互的必须定义 E2E 覆盖点；涉及性能指标的必须定义性能测试基线
- [ ] **Mock 数据需求**：列出测试所需的 fixture 用户、辅助数据集、外部服务 Mock 配置
  > **MAC**：每个 `card_type` 或核心状态至少对应一个 fixture 用户；跨日期测试必须提供时区/日期 fixture
- [ ] **测试执行检查清单**：可勾选的逐项验收列表，覆盖各分层测试的关键断言点
  > **MAC**：检查清单必须包含"状态机分支覆盖率"、"降级场景不返回 5xx"、"性能基线通过"三类必检项
- [ ] **可测性评审结论**：由 QA 或 Tech Lead 对 PRD 的 AC 进行可测性预审，标记"可直接翻译为测试用例"或"需要补充信息"的 AC

#### 验收标准

> SSOT 能把 AC 翻译成测试用例，**不需要发明新的验收点**、不需要问"这里要不要测并发"。

### 2.6 工程实施设计（Engineering Implementation Design）

**回答**："改哪些模块、关键实现决策是什么、依赖什么、失败怎么办"

#### 必输文档

| # | 文档 | 典型路径 | 作用 |
|---|------|---------|------|
| 6.1 | **实施范围声明** | PRD「范围界定」+ Tech Design「涉及模块」章节 | 预计修改的模块/目录/文件类型 |
| 6.2 | **关键实现决策记录** | Tech Design「决策」章节 或 `.planning/phases/*-CONTEXT.md` 的 `<decisions>` | 同步 vs 异步、立即生效 vs 延迟生效、乐观锁 vs 悲观锁等 |

#### 必输要素

- [ ] **实施范围边界**：涉及哪些模块、哪些目录预计会改、**哪些文件明确不碰**
  > **MAC**：范围精确到目录级别（如 `apps/api/internal/ai/service/`），至少列出 3 个预计修改的文件类型或目录
- [ ] **关键实现决策**（已拍板，SSOT 只记录不修改）：
  - 同步 vs 异步
  - 立即生效 vs 延迟生效 / 定时任务
  - 乐观锁 vs 悲观锁 vs 无锁
  - 软删除 vs 硬删除
  - 缓存策略（Redis key 结构、TTL）
- [ ] **依赖关系**：需要哪些前置 Phase / Feature / PR 先合并
- [ ] **回滚与降级策略**：发布失败如何回滚、功能异常如何降级（如：AI 失败时返回规则引擎结果还是错误）
- [ ] **性能与容量预估**：数据量、QPS、AI Token 消耗预估、存储增长预估

#### 验收标准

> SSOT 不需要决定"这个功能放在 Service 层还是 Handler 层"、不需要决定"用乐观锁还是悲观锁"。SSOT 只需把已确定的决策拆解为文件级任务。

## 三、SSOT：机械拆解与形式化（红色警戒线）

> **SSOT 的本质**：把 Pre-SSOT 阶段已确定的人类意图，转化为结构化的、可追溯的、可直接用于工程实施的形式化制品。
>
> **SSOT 不是再设计**。如果 Pre-SSOT 输入有矛盾、不清晰、缺要素，SSOT **必须阻塞并返回人类**，不得自行补全。

---

### 3.1 各维度 SSOT 机械任务清单

| 维度 | SSOT 负责（机械拆解） | SSOT 产出 |
|-----|---------------------|----------|
| **商业设计** | 从 PRD 提取结构化需求基线；按 Epic → Feature 层级拆解；为每个元素标注来源引用；补充编号、状态、优先级等元数据 | `docs/mvp-lite/business/`、`docs/mvp-lite/prds/` |
| **产品设计** | 把用户旅程转化为结构化用户故事列表；把业务规则转化为形式化规则表达式；补充边界条件（空值、极值、格式错误）；建立 PRD ↔ API ↔ TECH ↔ TESTSET 追溯链 | `docs/mvp-lite/prds/` |
| **UX 设计** | 把设计原则细化为组件规格（props、事件、样式参数）；把交互流程转化为页面状态机；把设计令牌映射为具体 CSS 变量值；按示例模式生成具体文案 | `docs/mvp-lite/ux/`、`docs/mvp-lite/ux-prototypes/` |
| **架构设计** | 把粗略 API 契约细化为精确字段（类型、必填、约束、示例值）；把存储思路转化为 Drizzle/Supabase schema 设计；把数据流转化为接口签名和调用顺序；补充错误码、状态码 | `docs/mvp-lite/tech/`、`docs/mvp-lite/api/`、`docs/mvp-lite/arch/` |
| **测试设计** | 把 PRD 的 AC 翻译为可执行的测试用例（Given-When-Then）；把风险场景转化为边界测试；补充前置条件、Mock 数据、期望结果；标注测试分层 | `docs/mvp-lite/testset/` |
| **工程实施** | 把 Tech Design 拆解为**文件级任务清单（Impl Package）**：改哪些文件、改什么、验收条件是什么；为每个任务标注依赖任务；把依赖关系转化为有向图；预估工时 | `docs/mvp-lite/tech/` 或模块实施说明 |
| **GSD 规划** | 基于 Impl Package 和现有代码上下文，制定**可执行的 Phase PLAN**：任务顺序、每步的 `files_modified`、现有模式复用点、集成点风险。**一个 Impl 包可拆分为多个 Phase 执行** | `.planning/phases/{nn}-*/` |

### 3.2 红色警戒线：SSOT 绝对禁止的行为

以下行为一旦在 SSOT 产出中出现，即视为**语义漂移**，必须回退修正。

#### 商业设计

- [ ] **禁止改变需求范围**：不能将 Out of Scope 的内容纳入 Feature，不能删除 In Scope 的内容
- [ ] **禁止新增/删除用户故事**：只能拆解/重组 PRD 中已存在的用户故事，不能发明新的业务场景
- [ ] **禁止修改成功指标**：不能更改目标值、测量方式或指标定义
- [ ] **禁止改变优先级**：不能把 P2 提升为 P0，除非 Pre-SSOT 文档已更新

#### 产品设计

- [ ] **禁止新增不在 PRD 中的用户故事**
- [ ] **禁止修改 AC 的业务意图**：可以细化测试步骤，不能改变"什么算验收通过"
- [ ] **禁止改变范围界定**：Out of Scope 的内容即使"看起来合理"也不能纳入
- [ ] **禁止修改业务规则中的公式/阈值/频率**：只能形式化表达，不能调整数值

#### UX 设计

- [ ] **禁止新增设计原则**：只能细化已有原则，不能发明新的 UX 理念
- [ ] **禁止改变颜色/图标/状态的语义映射**：如 `ready=绿色`、`blocked=红色` 已确定，不能修改
- [ ] **禁止发明新的交互模式**：如 Pre-SSOT 确定用"底部 Sheet"，SSOT 不能改为"弹窗"
- [ ] **禁止改变文案风格**：如确定用"教练口吻"，不能生成"系统通知式"文案

#### 架构设计

- [ ] **禁止改变技术选型**：不能替换框架、数据库、AI Provider
- [ ] **禁止新增/删除端点**：只能细化已有端点的字段，不能把 POST 改为 GET，不能新增未规划的端点
- [ ] **禁止改变同步/异步策略**：Pre-SSOT 确定异步的，SSOT 不能改为同步
- [ ] **禁止改变核心数据流方向**：不能新增未规划的中间层或绕开已有分层
- [ ] **禁止修改存储方案的核心选型**：如确定用 JSONB 的字段，不能改为规范化表，除非 Tech Design 明确允许

#### 测试设计

- [ ] **禁止新增未在 PRD 中约定的验收标准**
- [ ] **禁止把"可选"功能改为"必须"测试**：测试强度必须与优先级对齐
- [ ] **禁止降低已有 AC 的测试强度**：如 PRD 要求"并发安全"，Testset 不能忽略并发测试
- [ ] **禁止删除已规划的测试场景**

#### 工程实施

- [ ] **禁止新增未在 Tech Design 中的业务文件/模块**
  > **例外**：测试文件（`*_test.go`、Playwright spec）、Mock 文件、文档文件不受此限制——这些文件是测试和文档的必需产出，SSOT/GSD 可以根据需要新增
- [ ] **禁止把"修改"改为"重写"**：除非 Tech Design 明确要求重构
- [ ] **禁止删除已规划的测试任务**
- [ ] **禁止改变已拍板的关键实现决策**：如乐观锁不能改为悲观锁

## 四、语义漂移防控机制

### 4.1 输入输出一致性校验（SSOT 自验）

每个 SSOT 产出物必须包含 **来源追溯（Provenance）**：

```markdown
### 来源追溯
- 本 Feature 对应 PRD `docs/prd/xxx-prd.md` §3.2 用户故事 US-2
- 本 API 字段对应 Rough Tech Design `docs/tech/xxx.md` §4.1 核心字段定义
- 本测试用例对应 PRD 验收标准 AC-2.1
- 本业务规则对应 PRD §5.3 规则 R-03
```

**校验规则**：SSOT 产出中的每个关键元素（用户故事、字段、规则、测试用例）必须能追溯到 Pre-SSOT 文档的具体章节。**无法追溯的元素 = 漂移嫌疑**。

### 4.2 漂移检测清单（人工/AI 审核用）

在 SSOT 产出后、进入 GSD 前，运行以下检查：

- [ ] **范围漂移检测**：对比 SSOT 产出的 Feature 列表与 PRD Out of Scope 清单，确认无侵入
- [ ] **意图漂移检测**：随机抽取 3 条用户故事，对比 PRD 原文与 SSOT 拆解后的描述，确认业务意图未变
- [ ] **规则漂移检测**：对比 PRD 中的业务规则数值与 SSOT 形式化后的数值，确认阈值/公式一致
- [ ] **技术漂移检测**：对比 Rough Tech Design 中的端点列表与 SSOT 细化后的端点列表，确认无新增/删除
- [ ] **AC 漂移检测**：对比 PRD 中的 AC 与 SSOT Testset 中的测试用例，确认验收标准未加强/未削弱

### 4.3 阻塞升级策略

SSOT 在执行过程中遇到以下情况，**必须阻塞并返回人类确认**，不得自行发挥：

| 情况 | SSOT 行为 |
|-----|----------|
| Pre-SSOT 文档自相矛盾 | 标记矛盾点，列出冲突的文档章节，返回人类裁决 |
| Pre-SSOT 文档缺少必输要素 | 标记缺失项，引用本清单对应条目，返回人类补充 |
| 技术实现与 Pre-SSOT 决策冲突 | 标记冲突（如：Pre-SSOT 要求同步但发现必须异步），返回人类重新决策 |
| 发现更优方案但会改变意图 | **禁止擅自采用**。记录方案对比，通过 `ll-gate-human-orchestrator` 提交人工审批 |
| 边界条件在 Pre-SSOT 中未定义 | 列出边界场景，返回人类补充规则，不能假设默认值 |

### 4.4 变更控制（Change Control）

SSOT 过程中如果必须修改 Pre-SSOT 意图（如技术不可行）：

1. **SSOT 不得直接修改** Pre-SSOT 文档
2. 必须通过 **人工审批门控**（`ll-gate-human-orchestrator`）
3. 审批通过后，**先更新 Pre-SSOT 文档**，再重新运行 SSOT
4. 变更必须记录到 `docs/mvp-lite/arch/` 或对应模块治理文档

## 五、Post-SSOT / GSD：工程实施输入确认

SSOT 完成后、进入编码前，GSD 阶段必须确认以下输入已就绪：

### 5.1 GSD 必检清单

| # | 检查项 | 来源 | 缺失处理 |
|---|-------|------|---------|
| G1 | **Impl 包 / 技术实施说明** | `docs/mvp-lite/tech/` 或模块实施说明 | 阻塞：无实施说明无法拆解任务 |
| G2 | **Phase 上下文（CONTEXT）** | `.planning/phases/{nn}-*/{nn}-CONTEXT.md` | 阻塞：无上下文则不理解代码背景 |
| G3 | **Phase 计划（PLAN）** | `.planning/phases/{nn}-*/{nn}-{mm}-PLAN.md` | 阻塞：无计划则无任务分解 |
| G4 | **编码规范** | `AI_CONSTITUTION.md` + `AGENTS.md` | 强制读取：确保代码风格和命令入口一致 |
| G5 | **架构总览** | `docs/mvp-lite/arch/` 当前模块相关文档 | 强制读取：确保分层正确 |
| G6 | **AI 宪法** | `AI_CONSTITUTION.md` | 强制读取：确保不违反硬约束 |
| G7 | **构建与测试命令** | `AGENTS.md` | 强制读取：确保使用 `apps/ai-coach-skill` 的 npm 命令 |

### 5.2 GSD 全局必检项（每次编码前）

- [ ] 已读取 `AI_CONSTITUTION.md`
- [ ] 已读取 `AGENTS.md`
- [ ] 已读取当前模块 `docs/mvp-lite` 真源文档
- [ ] implementation 任务已运行 `npm run context:write -- implementation <module_id>`，并优先读取生成的 Impl Context Pack
- [ ] Git 工作区干净，当前分支正确
- [ ] 如需集成测试，确认 `apps/ai-coach-skill` 所需本地服务和环境变量已就绪

### 5.3 GSD 编码中的约束

- **发现 SSOT 产物有技术不可行之处** → 不得擅自绕过。记录问题，回退到 Pre-SSOT 重新决策
- **发现 SSOT 产物与现有代码冲突** → 优先遵循现有代码模式（Established Patterns），如需打破模式，走变更控制
- **需要新增未在 SSOT 中规划的文件** → 禁止。如需新增，先回退到 SSOT 补充 Impl 包

### 7.2 缺失处理策略汇总

| 级别 | 含义 | 处理方式 |
|-----|------|---------|
| **阻塞（Block）** | 必输文档/要素缺失，SSOT 无法启动或会自由发挥 | **拒绝进入 SSOT**，返回人类补充。AI 不得擅自填补 |
| **强制读取（Read）** | 已有文档，GSD 编码前必须浏览 | 读取并确认理解，不阻塞流程 |
| **漂移（Drift）** | SSOT 产出偏离 Pre-SSOT 意图 | **拒绝进入 GSD**，回退 SSOT 修正或返回人类重新决策 |
| **可接受（Optional）** | 对当前迭代非必需 | 不阻塞，按需读取 |

### 7.3 按场景简化路线

| 场景 | Pre-SSOT 重点 | SSOT 重点 | GSD 重点 |
|-----|--------------|----------|---------|
| **全新需求（从 0 开始）** | 全部 6 维度必输要素 | 完整 LL 工作流：raw→src→epic→feat→tech→testset→impl | 标准 Phase 执行 |
| **已有需求新增 Feature** | 2.2 用户旅程新增分支、4.5 粗略 API 新增端点、6.1 实施范围 | 增量 SSOT：feat→tech→testset→impl | 增量 Phase |
| **技术重构（无业务变更）** | 4.x 架构设计（新方案）、6.2 关键决策 | tech→impl（商业/产品/UX 可复用现有） | 重构 Phase |
| **Bugfix / 热修复** | 2.4 业务规则（确认触发条件）、6.1 范围（只改相关文件） | 可跳过 SSOT，直接 GSD-quick | `gsd-quick` |
| **LL 工作流产出（非编码）** | 对应上游输入 | 执行对应 LL Skill | 不适用 |
