# 文档类型必输章节规范

> 本文件汇总 DOC-WRITING-GUIDE 和 ITERATION-DOCUMENT-CHECKLIST 中每种文档类型的必输章节、可选章节和完整性要求。
> zdoc-write Phase 1 加载此文件确定文档结构。

---

## 通用必填章节（所有类型）

以下章节适用于除 `stg/`、`reviews/`、`ux-prototypes/` 之外的所有文档：

| 章节 | 说明 |
|------|------|
| **文档定位** | 一句话说明本文负责回答什么问题 |
| **关联文档** | 表格列出上下游文档 |
| **范围边界** | In Scope / Out of Scope |
| **术语或概念** | 本文引入的关键概念（如适用） |
| **验收或检查点** | 判断本文描述成立的条件 |
| **Open Questions / Assumptions** | 未决问题和假设 |

## 类型特定规范

### PRD — 产品需求文档 (`prds/`)

**命名**: `PRD-M{编号}-{Module-Slug}.md`

**必须包含**:
- 模块定位和一句话定义
- 非目标（Non-Goals）：明确列出不解决的问题
- 复用基线或历史背景
- 变更清单：新增、修改、删除
- 概念说明
- 用户故事（Priority + Acceptance Criteria），格式 `AS A... I WANT... SO THAT...`
- 用户旅程：主路径、分支路径、异常路径
- 功能需求（FR）和非功能需求（NFR）
- 成功指标与度量方案
- 数据模型摘要或关键字段来源
- API 摘要或接口需求
- 与上下游模块的边界契约
- 验收标准汇总
- Open Questions / Assumptions

**ITERATION-DOCUMENT-CHECKLIST 完整性要求** (§2.2):
- 问题陈述：背景、痛点、根本原因分析
- 用户故事：每条必须有 AC，AC 格式 Given-When-Then
- 范围界定：Out of Scope 必须具体
- 业务规则：每个阈值必须附带数据来源或假设说明
- 异常流程：必须覆盖业务异常 + 系统异常两层
- 状态转换：数据/页面/流程的状态变化条件
- 前后端交互场景清单

**可选包含**: ASCII UX 原型、Phase 2 升级路径、状态转换图、迁移说明

**不包含**: 完整 DDL、Repository 代码、端点级请求响应样例全集、组件级视觉 token

---

### Architecture — 架构设计 (`arch/`)

**命名**: `ARCH-LITE-{序号}-{Slug}.md` 或 `ARCH-M{编号}-{Module-Slug}.md`

**必须包含**:
- 背景与结论
- 目标和非目标
- 分层边界
- 目录结构或运行时结构
- 依赖策略
- 数据访问策略
- 安全、降级、成本、可观测性或事务策略
- 与 PRD / TECH / API 的关系
- 验收门槛或架构守则

**ITERATION-DOCUMENT-CHECKLIST 完整性要求** (§2.4):
- 技术选型声明：语言版本、框架、数据库、AI Provider、关键第三方库
- 架构分层与职责边界
- 同步/异步策略
- 核心数据流
- 粗略 API 契约
- 前后端交互时序图（Mermaid/PlantUML）
- 存储方案思路
- 非功能性需求：性能、安全、并发、降级
- 集成点与外部依赖

**可选包含**: 时序图、决策记录、冲突处理、环境变量策略、Feature Flag

**边界**: arch/ 回答"系统整体怎么切、跨模块约束是什么"；tech/ 回答"单个模块内部怎么实现"

**不包含**: 单端点完整请求响应样例、组件级视觉设计、具体测试用例列表

---

### API — API 契约 (`api/`)

**命名**: `API-M{编号}-{Module-Slug}.md` 或 `API-{序号}-{slug}.md`

**必须包含**:
- 文档定位和关联 PRD / TECH / ARCH
- API 清单：方法、端点、描述、请求 schema、响应 schema、错误码、优先级
- 鉴权方式
- 通用错误响应
- 每个端点的请求头、请求体、字段说明
- 成功响应和主要错误响应示例
- 幂等、速率限制、权限、设备指纹或会话约束
- 与前端 CardAction、Skill 或 Service 的调用边界
- **变更说明**（强制）：必须包含"变更说明"章节或"首次撰写"标注。涉及旧接口变更时，列出完整变更清单（新增/修改/删除/重命名/类型变更/行为变更）、破坏性变更确认、迁移注意事项、旧文档中未提及的端点

**可选包含**: JWT payload 规范、缓存策略、响应头约定、迁移兼容说明

**不包含**: 完整业务推导过程、UI 视觉规则、内部 Repository 实现、Skill 内部推理步骤

---

### UX — UX 设计规范 (`ux/`)

**命名**: `UX-M{编号}-{Module-Slug}.md`

**必须包含**:
- 设计原则：系统级继承和模块特有原则
- 交互流程：步骤、用户动作、系统响应、视觉变化
- 状态表达：加载、成功、失败、空状态、阻断态
- 组件结构或页面结构
- 设计令牌使用：颜色、间距、字体、状态色
- 响应式或移动端约束
- 与原型、PRD、设计系统的关联

**ITERATION-DOCUMENT-CHECKLIST 完整性要求** (§2.3):
- 设计原则：至少 3-5 条，每条有说明 + 体现示例
- 核心页面交互流程
- 状态表达规则
- 设计令牌引用
- 文案风格指南：口吻、禁忌词、微文案示例（≥3 场景覆盖正常/警告/错误）
- 平台差异策略
- 错误状态 UX 规范

**可选包含**: 动效规范、可访问性要求、文案规则、QA 检查清单

**不包含**: 后端接口完整契约、数据库表结构、商业目标详细论证

---

### Tech — 技术实现设计 (`tech/`)

**命名**: `TECH-M{编号}-{Module-Slug}.md`

**必须包含**:
- 文档定位和关联 PRD / API
- 数据模型 / Schema
- 状态机或核心状态枚举
- 关键业务规则和算法
- 输入校验和边界值
- 幂等、事务、并发、错误处理
- 数据写入与读取路径
- 与 Service、Repository、Adapter、Skill 的边界
- 非功能要求：性能、可靠性、安全、可观测性

**可选包含**: TypeScript interface、SQL / DDL 草案、决策表、伪代码、迁移和回滚策略

**不包含**: 产品价值论证、视觉设计细节、测试用例全集、与本模块无关的基础设施重构

---

### Testset — 测试策略与用例集 (`testset/`)

**命名**: `TESTSET-M{编号}-{Module-Slug}.md`

**必须包含** (9 个标准章节 + 附录):

1. **测试范围** — In Scope / Out of Scope
2. **测试策略** — 测试分层策略（单元/集成/E2E/性能/契约 5 层）、执行顺序（单元→集成→E2E→性能→安全）、并行/串行策略、失败重试与阻断条件
3. **测试用例** — 按类型分节：
   - 3.1 Happy Path 端到端测试
   - 3.2 边界条件测试（空值、极值、超长字符串、并发请求）
   - 3.3 异常路径测试
   - 3.4 状态机边界测试（如适用）
   - 3.5 安全与权限测试
   - 3.6 跨域读写边界测试
   - 3.7 性能测试
   - 3.8 AI 不确定性场景（AI 失败、格式异常、超时；纯规则模块标 N/A）
4. **测试数据** — fixture 清单、数据隔离策略、清理策略
5. **环境需求** — 数据库（类型/版本/连接）、缓存、测试框架、外部服务 Mock、CI/CD 环境、数据隔离策略
6. **执行计划** — 执行顺序、依赖关系、并行策略、失败重试、阻断条件
7. **准入/准出标准** — 准入条件（DB 迁移完成、fixture 加载成功等）、准出条件（通过率、性能指标、BLOCK 级 issue 清零）、阻断条件
8. **风险与应对** — 风险/影响/缓解措施三列表（环境不一致、Fixture 过期、Flaky 测试、Mock 不准确等）
9. **质量指标** — 指标/目标/说明三列表（覆盖率、通过率、P95 响应时间、测试执行总时间等）

**附录**:
- 附录 A: 测试执行检查清单（可勾选验收项）
- 附录 B: Traceability Matrix（PRD AC → TESTSET 用例映射）
- 附录 C: 变更日志

**ITERATION-DOCUMENT-CHECKLIST 完整性要求** (§2.5):
- 每条 AC 必须通过"可测三问"：测什么？怎么触发？怎么判定通过？
- Traceability Matrix：PRD AC → TESTSET 用例映射
- 清理策略：涉及写操作的用例必须指定清理资源

**可选包含**: 可测性评审结论、前端交互测试、可观测性测试、回归测试矩阵

**边界**: testset/ 回答"测什么、怎么测、怎么判定"；不回答"怎么实现"（用 tech/）

---

### Data — 数据流设计 (`data/`)

**命名**: `DataFlow-{Flow-Slug}.md`

**必须包含**:
- 文档视角：以数据实体为第一视角
- 设计目标
- 上游文档
- 已知 Schema 不对齐或冲突说明
- 宏观数据流图
- 数据实体清单：产生阶段、持久化位置、消费方、生命周期
- 每个实体的 Schema、来源、值域、必填性
- 数据缺失策略：Default / Fallback / Reject
- 存储、审计、幂等和时区规则
- 跨模块字段映射

**可选包含**: 阶段化执行流程、状态枚举映射、数据质量检查、审计表设计

**不包含**: 用户故事全集、视觉原型、单端点完整 API 文档

---

### DDD — 领域模型设计 (`ddd/`)

**命名**: `DDD-S{起始}-S{结束}-{Domain-Slug}.md`

**必须包含**:
- 领域定位与职责
- 不可违反约束
- 功能边界和跨域边界
- 核心实体、值对象、数据结构
- Service 函数接口
- 输入输出契约
- 领域流程和状态转换
- 上下游依赖
- 验收标准

**可选包含**: 训练学原理、LLM 介入判断、领域规则表、附录、评审发现、冻结决策

**不包含**: 页面流程和 UI 文案、API transport 细节、外部 Provider 协议细节

---

### Skill — AI Skill 设计 (`skills/`)

**命名**: `SKILL-{序号}-{slug}.md`

**必须包含**:
- ARCH 前置检查：确认该能力应该是 Skill 而非 API/Tool
- Skill 概述：一句话定义、业务定位、核心属性
- 输入 Schema、输入来源、输入校验
- 输出 Schema、前端卡片映射、副作用
- 调用方式：触发途径、接口暴露方式、调用时序
- 内部流程与步骤
- 涉及的 Domain Service、LlmPort、Repository / Adapter 调用
- 示例：典型调用、边界案例
- 上下游关系
- 安全与治理：幂等、安全门禁、降级
- 错误码和变更日志

**可选包含**: 状态机、时序图、LLM prompt 策略、配额/成本/灰区判断

**不包含**: 纯只读查询、确定性表单写入、无 LLM 判断的流程

---

### Adapter — 外部 Provider Adapter 设计 (`adapters/`)

**命名**: `ADAPTER-M{编号}-{provider}.md`

**必须包含**:
- 定位：Adapter 在调用链中的位置
- 边界：做什么 / 不做什么
- TypeScript 接口
- 外部 MCP / SDK / API 调用映射
- 输出到 Normalizer 或上游服务的契约
- 错误映射
- 安全和凭证处理边界

**可选包含**: Provider 可用性判断、rawPayload 保留策略、字段映射表

**不包含**: 业务决策、用户解释、直接前端服务、Skill 调用逻辑

---

### Job — 后台任务设计 (`jobs/`)

**命名**: `JOB-M{编号}-{slug}.md`

**必须包含**:
- 定位：Job 在系统链路中的位置
- 非 Skill 边界
- 触发方式：API、Cron、EventBus、用户动作
- 输入输出接口
- 执行流程
- 幂等策略
- 错误处理
- 审计日志和可观测性

**可选包含**: 重试策略、并发控制、任务拆分和队列策略、降级或部分成功策略

**不包含**: 前端交互细节、产品用户故事全集、Provider 协议细节

---

### Business — 模块商业设计 (`business/`)

**命名**: `BUSINESS-M{编号}-{Module-Slug}.md`

**必须包含**:
- 问题域：该模块解决的商业问题
- 业务目标：指标、目标值、验收标准
- 目标用户和角色
- 触发场景和关键用户旅程
- In Scope / Out of Scope
- 与战略宪法的映射
- 替代方案分析（Jobs-to-be-Done 框架）
- MVP 假设与验证计划
- 成本预估：开发、运营、LLM 调用、用户获取

**可选包含**: 商业漏斗、运营后台工具需求、付费或留存假设、风险和反功能

**不包含**: 详细 API 字段、数据库 schema、技术实现算法、视觉样式细节

---

### Strategy — 战略与商业宪法 (`stg/`)

**命名**: 自定义（如 `跑步大师商业落地宪法——{篇章名}篇 v{major.minor}.md`）

**必须包含**:
- 版本或变更日志
- 依赖声明
- 核心原则、明确不做什么、阶段性目标
- 风险、缺口、待决策项

**可选包含**: 市场判断、竞品判断、融资或国际化策略、指标字典、用户分层

**不包含**: 端点定义、代码级接口、DDL、测试用例细节、模块内局部流程的完整 PRD

---

### Req — 需求来源文档 (`reqs/`)

**命名**: `REQ-{source}-{YYYYMMDD}-{Slug}.md` 或 `REQ-M{编号}-{Slug}.md`

**必须包含**:
- 文档定位：一句话说明本文记录什么需求来源及其核心价值主张
- 需求来源：来源类型、提供方、获取方式、原始出处、获取日期（表格形式）
- 原始需求描述：保留原始语言（不翻译为产品术语），包含上下文背景和相关方
- 痛点或机会分析：痛点描述、机会描述、现有替代方案
- 初步价值判断：用户价值、商业价值、技术可行性、合规/风险因素（四维度表格）
- 转化为 PRD 的关键问题：需要在 PRD 阶段回答的问题清单
- 关联文档：主要是下游 PRD 的引用
- 范围边界：In Scope / Out of Scope（初步范围判断，Out of Scope 至少 3 项）
- 验收或检查点：需求来源确认、完整性、转化决策（可勾选检查项）
- 变更日志：日期/变更/变更人

**Frontmatter 特殊字段**:
- `source_type`: `user_feedback` | `expert_knowledge` | `market_research` | `competitor` | `internal` | `regulatory` | `process` | `data_driven`
- `source_url`: 外部链接（如有）
- `source_contact`: 需求提供方
- `confidence`: `high` | `medium` | `low`（需求可信度）
- `urgency`: `high` | `medium` | `low`（紧急程度）
- `related_prd`: 已转化的 PRD 列表

**可选包含**: 访谈纪要原文、用户原话引用、截图/录屏描述、数据支撑、竞品对标细节

**边界**: reqs/ 回答"我们听到了什么、为什么值得做"；prd/ 回答"我们要做什么、怎么做"

**不包含**: 用户故事（用 PRD）、AC（用 PRD）、API 字段、技术实现方案、视觉设计

**与 PRD 的关系**:
- 一个 req 可转化为 1 个或多个 PRD
- PRD 的 `relationships.depends_on` 应指向关联的 req
- req 的状态流转：`draft` → `reviewed`（已评估） → `converted`（已转 PRD） / `rejected`（不转化）

### Review — 审查与对齐报告 (`reviews/`)

**命名**: `Review-{scope}.md` 或 `Cross-Review-{scope}-Round{n}.md`

**必须包含**:
- 评审日期
- 评审范围
- 变更主题或审查目标
- 核心结论
- 文件变更清单或覆盖检查
- 不一致、风险、缺口
- 修复建议或后续行动
- 架构纪律确认

**可选包含**: 字段覆盖矩阵、决策前后对比、多轮审查记录、验证证据

**不包含**: 未经 PRD/ARCH 接受的新需求、完整 API 或 TECH 重写

---

### UX Prototype — 静态视觉原型 (`ux-prototypes/`)

**命名**: `proto-m{编号}-{slug}.html`

**HTML 原型必须**:
- 可直接在浏览器打开
- 标明或通过索引映射对应 PRD
- 覆盖关键状态（不只是 happy path）
- 使用统一设计系统

**`_index.md` 必须**: 列出原型、标明 PRD、说明使用方式

**`_design-system.md` 必须**: 定义色彩、字体、布局、组件、状态色

---

### Impl — 实施设计 (`tech/`)

**命名**: `IMPL-M{编号}-{Slug}.md`

**必须包含**:
- 实施范围边界
- 关键实现决策
- 依赖关系
- 回滚与降级策略
- 性能与容量预估

**ITERATION-DOCUMENT-CHECKLIST 完整性要求** (§2.6):
- 实施范围精确到目录级别
- 关键实现决策已拍板（同步/异步、锁策略、缓存策略等）
- 依赖关系已明确
- 回滚与降级策略已确定

## 完整性检查清单

### 新增文档前检查

1. 确定文档类型 → 加载对应必输章节
2. 确定模块编号 → 填入 frontmatter `module_id`
3. 确定层级 → 填入 frontmatter `layer`
4. 确定优先级 → 填入 frontmatter `priority`

### 输出前检查

1. Frontmatter 包含 title、status、created
2. 所有必输章节已生成（无遗漏）
3. 无占位符残留（`TODO`、`TBD`、`{placeholder}` 已处理）
4. 命名符合 DOC-WRITING-GUIDE §0.6
5. 交叉引用格式正确
6. 不包含其他类型文档的专属内容
7. Out of Scope 至少列出 3 项具体内容
8. Open Questions / Assumptions 已记录（或明确无未决问题）
9. **API 文档变更检测**：API 文档必须包含"变更说明"章节或"首次撰写"标注
10. **破坏性变更确认**：检测到破坏性变更（删除端点、字段类型变更、行为变更）时，决策摘要中必须包含确认项
11. **旧文档关联**：涉及变更时，frontmatter `related_docs` 和 `relationships.supersedes` 必须关联旧文档
